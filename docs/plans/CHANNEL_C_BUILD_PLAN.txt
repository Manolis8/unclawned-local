CHANNEL C — BUILD PLAN
"What the Agent Observes" — The environment reveals the mind.
Implementation from zero to working signal
═══════════════════════════════════════════════════════════════════════════════

Channel A reads what they TYPE. Channel B reads how they REACT.
Channel C reads what WORLD they inhabit while doing both.

The world is: what apps are open, what domains they work on, how their
Desktop is structured, what tools they use repeatedly, what platforms
they live in vs. visit occasionally.

This is passive intelligence — collected not from messages, but from
what the agent OBSERVES when it executes tasks on the user's behalf.

Why Channel C is different from A and B:
  — Channels A and B mine text. Channel C mines environment.
  — Signals come from AGENT ACTIONS, not user messages.
  — The browser agent sees domains. The local agent sees files/apps.
  — No NLP needed — pure structural classification.
  — One clear snapshot per task reveals more than parsing 100 prompts.

What Channel C tells the agent:
  1. What tool stack defines this person's work world
     → Don't suggest tools they don't use. Do reference their real tools.
  2. What domains they live in vs. visit for tasks
     → Notion.so appearing in 40% of browser tasks = they live in Notion.
  3. What their Desktop looks like (organized vs. chaos)
     → Systematic vs. fluid thinker. Affects how you present output.
  4. Which file types they work with most
     → Heavy .xlsx user = data-driven. Heavy .md = developer/writer mindset.
  5. What time patterns their work sessions follow
     → Task at 6pm = after-hours worker. Task at 9am = standard schedule.

PART 0 — ARCHITECTURE DECISIONS

──────────────────────────────────────────────────────────────────────────────
DECISION 1: WHERE DO CHANNEL C SIGNALS COME FROM?
──────────────────────────────────────────────────────────────────────────────

Channel C signals come from THREE observation sources:

  SOURCE 1: BROWSER TASK EXECUTION
  When the agent visits websites to complete a task, it sees:
  — Which domains were touched during task execution
  — What type of site each domain is (productivity, social, data, dev...)
  — How many domains were required for a task (simple vs. multi-step research)

  These are already partially available: the agent uses Playwright and visits
  pages. The hook: after task completion, log which domains were navigated.

  SOURCE 2: LOCAL TASK EXECUTION
  When the agent reads/writes files to complete a task, it sees:
  — Which directories were touched (Desktop, Documents, specific project folders)
  — What file types were accessed (.xlsx, .md, .pdf, .py, .csv...)
  — What the target folder structure looks like (depth, naming patterns)

  Hook: after any read_file, write_file, or list_directory tool call,
  log the path, extension, and folder depth.

  SOURCE 3: ON-DEMAND DESKTOP SCAN
  Once at session start (or when first task runs), do a shallow scan:
  — Desktop file count and types
  — Home directory top-level folder names
  — Recently modified folders (signals active projects)
  — Running processes (signals installed/active apps)

  This is the richest signal per call but also the most privacy-sensitive.
  Run once per session, store the summary (not raw paths).

→ BUILD CHOICE: All three sources. Sources 1 and 2 are automatic (hooks on
  existing tool calls). Source 3 is once-per-session scan on task start.

──────────────────────────────────────────────────────────────────────────────
DECISION 2: WHAT DATA MODEL FITS ENVIRONMENT SIGNALS?
──────────────────────────────────────────────────────────────────────────────

Environment signals are STRUCTURAL, not NLP. They need:
  — A table for raw observations (one row per task execution)
  — A table for domain logs (domains seen across many tasks)
  — A table for file type logs (file types touched across many tasks)
  — A table for compiled profiles (one row per user)

Unlike A and B where one row = one message, here one row = one task session.
A task session may have multiple domain visits and file accesses.

Store domains and file types as JSON arrays in the raw row.
Maintain separate domain_log and file_type_log for aggregation.

──────────────────────────────────────────────────────────────────────────────
DECISION 3: PRIVACY DESIGN
──────────────────────────────────────────────────────────────────────────────

Channel C has higher privacy surface than A and B.
The user hasn't "typed" this data — we're observing their environment.

Safeguards:
  — Never store full file paths — store only the folder name and file extension
    Example: store "Documents/Projects" NOT "C:\Users\manol\Documents\Projects\client-x\invoices\2024-oct.xlsx"
  — Desktop scan: store counts and types, not names
    Example: store {pdf: 3, xlsx: 5, folder_count: 12} NOT filenames
  — Running processes: store category (dev-tools, productivity, browser...) not raw exe names
    unless the exe maps to a known tool (notion.exe → Notion ✓)
  — Domain log: store domains (notion.so) not full URLs (notion.so/workspace/abc-private-page)
  — No calendar content, no email content, no message content (those are D-E-F territory)

This is behavioral fingerprinting at the STRUCTURAL level only.

──────────────────────────────────────────────────────────────────────────────
DECISION 4: HOW DOES COLLECTION FIT THE EXISTING ARCHITECTURE?
──────────────────────────────────────────────────────────────────────────────

The existing agent task flow (for browser + local tasks):
  1. User sends message → /chat route
  2. Orchestrator routes to browser or local
  3. Agent executes tool calls (Playwright, file tools)
  4. Agent returns result
  5. Response sent to user

Channel C hooks at step 3-4:
  — After browser tool calls: log visited domains
  — After local tool calls: log file paths accessed
  — Before step 3 (session start): optional desktop scan

Hook mechanism: same pattern as Channels A and B — fire-and-forget extraction
that never blocks the response path.

The difference: A and B hook into the /chat route (messages).
Channel C hooks into the SKILL EXECUTION layer (the agent tool loop).

→ BUILD CHOICE: Hook into runAgentLoop (or wherever the agent's tool calls
  are processed) to capture environment observations as a side effect.

TABLE 1: channel_c_task_snapshots
──────────────────────────────────────────────────────────────────────────────

One row per agent task execution. Captures environment observations for that task.

CREATE TABLE IF NOT EXISTS channel_c_task_snapshots (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  session_id TEXT,
  created_at TEXT DEFAULT (datetime('now')),

  -- Task context
  task_type TEXT,                     -- browser | local | hybrid
  task_hour INTEGER,                  -- 0-23, hour of day task was run
  task_day_of_week INTEGER,           -- 0=Sunday ... 6=Saturday

  -- Browser observations (populated for browser/hybrid tasks)
  domains_visited TEXT,               -- JSON array of domain strings
  domain_categories TEXT,             -- JSON array of category strings (deduped)
  primary_domain TEXT,                -- most-visited domain in this task
  domain_count INTEGER DEFAULT 0,

  -- Local observations (populated for local/hybrid tasks)
  file_extensions TEXT,               -- JSON array of extensions touched (e.g. [".xlsx", ".pdf"])
  folder_names TEXT,                  -- JSON array of folder names accessed (not full paths)
  file_count INTEGER DEFAULT 0,

  -- Desktop scan (populated once per session, first task only)
  desktop_scanned INTEGER DEFAULT 0,  -- 1 if scan was performed this task
  desktop_file_types TEXT,            -- JSON: { ext: count } e.g. {"pdf": 3, "xlsx": 5}
  desktop_folder_count INTEGER,
  home_top_folders TEXT,              -- JSON array of top-level folder names in home dir
  active_app_categories TEXT,         -- JSON array of app categories running at scan time

  -- Error handling
  extraction_error TEXT
);
CREATE INDEX IF NOT EXISTS idx_cc_snap_user ON channel_c_task_snapshots(user_id);
CREATE INDEX IF NOT EXISTS idx_cc_snap_created ON channel_c_task_snapshots(created_at);
CREATE INDEX IF NOT EXISTS idx_cc_snap_type ON channel_c_task_snapshots(task_type);

CREATE TABLE IF NOT EXISTS channel_c_domain_log (

CREATE INDEX IF NOT EXISTS idx_cc_domain_domain ON channel_c_domain_log(domain);

──────────────────────────────────────────────────────────────────────────────
ENV SCANNER (once per session)
──────────────────────────────────────────────────────────────────────────────

Runs once at task start if no scan exists for this session.
Uses PowerShell on Windows (already the agent's shell layer).

What it collects:
  1. Desktop file types: Get-ChildItem Desktop — count files by extension
  2. Home top folders: Get-ChildItem ~ -Directory — names of top-level folders
  3. Active apps: Get-Process | Sort-Object CPU -Desc | Select-Object -First 20
     → map exe names to app categories using app-categories.json
  4. Recent files (modified in last 7 days): quick scan of Desktop + Documents

Privacy filter: no full paths, no filenames — only extensions and folder names.

──────────────────────────────────────────────────────────────────────────────
DOMAIN EXTRACTOR
──────────────────────────────────────────────────────────────────────────────

Hook into the browser tool calls. After each page navigation during task:
  — Extract domain from URL
  — Classify domain using domain-categories.json
  — Add to the task's domain list

Domain extraction: just hostname from URL (strip protocol, path, query)
  "https://app.notion.so/workspace/abc" → "notion.so"
  "https://github.com/user/repo/issues/1" → "github.com"

The hook point: the Playwright wrapper (pw-tools-core) already has navigate/visit calls.
After each successful navigate, fire the domain extraction.

──────────────────────────────────────────────────────────────────────────────
FILE CLASSIFIER
──────────────────────────────────────────────────────────────────────────────

Hook into local file tool calls. When the agent reads/writes a file:
  — Extract file extension
  — Classify using file-type-categories.json
  — Extract the immediate parent folder name (not full path)
  — Add to the task's file access list

Hook point: the read_file, write_file, list_directory tools in the agent.
After each file tool call, log the accessed extension and folder name.

Unlike A and B (triggered on incoming message), Channel C is triggered on
task COMPLETION. The extractor receives the collected observations from tool
calls that happened during the task and packages them into a snapshot row.

Extractor inputs (from task context, accumulated during execution):
  — userId, sessionId, taskType
  — domainsVisited: string[]       (from domain-extractor hook)
  — fileExtensions: string[]       (from file-classifier hook)
  — folderNames: string[]          (from file-classifier hook)
  — desktopScan?: DesktopScanResult (from env-scanner, once per session)

Pipeline:
  1. Classify all domains → domain_categories[]
  2. Identify primary domain (most frequent)
  3. Compute hour + day of week (from current time)
  4. Build the snapshot row
  5. Insert into channel_c_task_snapshots
  6. Upsert domain log rows (one per unique domain)
  7. Update profile

TOOL STACK PROFILE
──────────────────────────────────────────────────────────────────────────────

PART 7 — PROBLEMS AHEAD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

──────────────────────────────────────────────────────────────────────────────
PROBLEM 1: AGENT BROWSES FOR THE USER, NOT LIKE THE USER
──────────────────────────────────────────────────────────────────────────────

What happens: User asks "research what Notion alternatives exist."
Agent visits notion-alternatives.com, productcompare.io, Reddit, etc.
These domains are research/content domains — but the user doesn't actually
use these sites. The domain log fills up with research artifacts, not
user's real tool stack.

Solution: Tag each domain with the TASK CONTEXT.
  is_research_task: boolean (was this domain visited to gather info vs. to perform a task?)

  Research tasks: log domains but DON'T count toward tool_stack_profile
  Action tasks ("post this to LinkedIn", "update my Notion page"): DO count
  Mixed: split by task phase (research phase vs. action phase)

  Classification: if task_type = 'research' or the agent's first action on
  that domain was a "read/search" action (not a form fill or click-to-action),
  mark as research_artifact = true in the domain log.

  tool_stack_profile uses only domains where research_artifact = false.

──────────────────────────────────────────────────────────────────────────────
PROBLEM 2: DESKTOP SCAN IS A ONE-TIME SIGNAL THAT GOES STALE
──────────────────────────────────────────────────────────────────────────────

What happens: Desktop was scanned 2 months ago. User has completely
reorganized. The profile shows "cluttered" when desktop is now clean.

Solution: Re-scan every 14 days.
  Store last_scan_at in desktop_profile.
  Before each task: check if last_scan_at < 14 days ago. If so, re-scan.
  The re-scan is cheap (PowerShell count + list operation, no content read).

──────────────────────────────────────────────────────────────────────────────
PROBLEM 3: RUNNING PROCESSES LIST IS NOISE
──────────────────────────────────────────────────────────────────────────────

What happens: Get-Process returns 80+ processes. Most are system/background
(svchost, RuntimeBroker, antivirus, etc.). These have no signal value.

Solution: Allowlist-only approach for process classification.
  Only count processes that appear in app-categories.json.
  Everything else is discarded.
  This means we never "discover" new tools from raw process names —
  but we also never classify "MsMpEng.exe" as meaningful.

  The app-categories.json is the knowledge base. Keep it updated.

──────────────────────────────────────────────────────────────────────────────
PROBLEM 4: WORK TIME PROFILE WRONG FOR MULTI-TIMEZONE USERS
──────────────────────────────────────────────────────────────────────────────

What happens: User travels frequently. Task at 9am in NY = 3pm in London.
The hour distribution is meaningless if the server records UTC.

Solution: Record LOCAL hour from the client.
  The local PC agent knows the local time — use it.
  Pass localHour (0-23 in user's timezone) in the snapshot.
  Server stores task_hour as localHour, not UTC hour.

  Simple implementation: local agent sends localHour = new Date().getHours()
  when it fires the task snapshot. Server stores it verbatim.

──────────────────────────────────────────────────────────────────────────────
PROBLEM 5: HOOK POINT DOESN'T EXIST YET IN AGENT EXECUTION
──────────────────────────────────────────────────────────────────────────────

What happens: Channel C needs to intercept tool calls as they happen during
agent execution. But runAgentLoop is a tight loop with no current hook for
side-channel observation.

Solution: Add a lightweight observation accumulator.
  ChannelCAccumulator class: holds state for one task execution.
    .addDomain(domain: string): void
    .addFileAccess(path: string): void
    .setDesktopScan(scan: DesktopScanResult): void
    .flush(userId, sessionId, taskType): Promise<void>  ← fires at task end

  Pass accumulator into runAgentLoop as an optional parameter.
  Tools call accumulator.addDomain() / addFileAccess() after each tool call.
  At task completion, call accumulator.flush().

  This is cleaner than a global side-channel and doesn't require
  restructuring runAgentLoop.

THE ONE THING THAT MAKES CHANNEL C WORK OR NOT WORK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The research artifact filter (Problem 1).

Without it, every research task poisons the tool stack profile with
domains the user doesn't actually use. A research task visiting
20 sites fills the domain log with noise.

With it, tool stack = only domains where the agent PERFORMED AN ACTION
for the user (not gathered information about). These domains are the user's
real workflow.

The filter requires knowing WHY the agent visited each domain.
Tag visits at collection time: visited_to_read vs. visited_to_act.
"visited_to_act" domains build the tool stack. "visited_to_read" = research artifacts.

That one bit of context turns a noisy domain log into a precise tool profile.
